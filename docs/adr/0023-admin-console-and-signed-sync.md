# 0023. The admin console: its own workspace, signed releases, devices that sync in the background

Status: **Accepted** for the first slice (policy, catalog and fleet pages;
signing; device sync; `catalog.search`). PRD AD-1 … AD-5, AD-10, DV-1,
DV-3, DV-10, DV-11, GA-2, EP-12. Builds on ADR 0021 (managed settings
load from disk) and ADR 0008 (declared privileges).

## Context
IT needs one web console to set agent policy per group (AD-1, AD-2),
version, preview and stage it (AD-3), approve and publish catalog items
per group (AD-5, DV-10, DV-11), and see the fleet (AD-4). Devices must
apply what IT publishes without trusting the network in between (DV-1,
EP-12), keep booting from disk and keep working offline (ADR 0021). Agents
building an app must first look for an approved one (GA-2).

The console is not part of the OS image. In production it is one of our
cloud services (GT-21, on AWS); devices reach it over HTTPS. It needs an
HTTP server stack that nothing on a device should compile or link.

## Decision

### Where it lives
- **`console/` is its own Cargo workspace**, like `shell/` (ADR 0009):
  `make build test lint` never compile its HTTP server (axum, hyper,
  tower), the FreeBSD clippy pass never sees it, and its lock file and
  `deny.toml` are its own. It reaches the core only through lib crates by
  path: `glass-managed` (the contract), `glass-policy` (the same
  validation devices run, so the console never signs a policy a device
  would reject) and `glass-types`.
- **`glass-managed`** (`crates/lib/managed`) is the contract, as
  `glass-api` is for the shell: the signed envelope, the catalog item and
  its declared privileges, catalog-first search, the sync and report
  messages, and the device's store of applied releases.
- The **web UI** is TypeScript with no framework, bundled by esbuild into
  one script and one stylesheet (`console/web`), served by the console.
  Playwright drives it in headless Chromium for the end-to-end tests.

### The console
- One process, `glass-console serve`, keeping its state as JSON files in a
  directory (a stand-in for the managed database GT-21 calls for). It
  serves the admin API (`/api/…`), the device API (`/device/v1/…`) and
  the UI. It binds to loopback by default: IT sign-in (SSO) is not built.
- **Groups come from a `Directory`** (`console/crates/glass-console/src/
  directory.rs`): today a local file (`directory.toml`), later SCIM from
  Entra ID or Okta (AD-1) behind the same trait. Until devices get group
  membership another way, a published policy inlines each group's
  `members`, because the device's policy engine reads them (`groups_of`).
- **A policy draft is a `PolicyDocument`**, edited in place; there is no
  parallel schema. *Preview impact* compares the draft with what the
  broad ring runs: the users in changed groups (everyone, for org-wide
  changes) and the agents whose rules changed, with the changes in plain
  words and `Policy::lint`'s warnings.
- **Versions and rings (AD-3).** *Publish* validates the draft with
  `glass-policy`, signs it as the next version and releases it to the
  pilot ring; *Promote* moves it to early, then broad. A device gets the
  newest version its ring has reached. *Roll back* signs the previous
  version's content again as a new version and releases it to every ring
  at once: versions only ever go up.
- **Catalog (AD-5, DV-10, DV-11).** Items carry versions, their declared
  privileges (DV-3) and a review state (waiting, approved, blocked); IT
  sets, per group, required, available or blocked. The signed catalog
  release holds only approved items and goes to every ring at once when
  IT decides: approvals and blocks are not staged. (Item version rings and
  pinning are DV-12, P1.) Items signed with the org's key are marked
  `internal` and are never publicly listable (DV-10).
- **Fleet (AD-4, AD-10 stub).** A device enrolls by sending its first
  report with the org's enrollment token; the fleet view aggregates
  reports: running agents, people waiting, policy blocks in 24 hours,
  versions in force per ring. Zero-touch enrollment and per-device
  credentials are not built.

### Signing (DV-1, DV-10, EP-12)
- The org's **ed25519 key** is generated by the console on first start
  and kept in its state directory (mode 0600), never on a device
  (`ed25519-compact`: MIT, no dependencies). Hardware keys and key
  ceremonies (EP-11) replace this file later.
- A release is an envelope that signs the document **kind, org, version,
  issue time and payload SHA-256**. A catalog can't pass for a policy,
  one org's release can't be replayed at another's devices, and a device
  refuses any version not above the one it has, so an old release can't be
  replayed to undo a newer one.
- Devices trust the **public keys in their own `glassd.toml`**
  (`[managed] org_keys`, written at enrollment), never a key a response
  names. Several may be listed, so the org key can rotate (EP-12).

### Devices (ADR 0021's proposals, now built)
- **Boot is unchanged**: glassd starts from the policy file on disk, the
  last good one if it doesn't validate. The catalog last applied is read
  from `<state_dir>/managed/` and checked again once glassd is up.
- **After glassd is up**, a background task long-polls the console
  (`GET /device/v1/sync`, waiting up to 25 s for something newer), so an
  online device has a release about a second after IT publishes it to its
  ring. Each release is verified, then validated whole: the policy text
  with `glass-policy` and linted against an action registry built from it,
  then written with `PolicyStore::apply` (the previous version kept) and
  swapped into the runtime with the registry in one step. Tasks started
  after use it; running tasks keep the effective policy they started with.
  Every apply and refusal is audited (`PolicyLoaded` with `source:
  managed`, `CatalogLoaded`).
- **Offline**, a failed sync backs off (2 s doubling to 5 minutes) and
  changes nothing: the device enforces what it last applied, and says why
  in `glassctl status`. A refused release is reported to the console
  (`last_error`) and the device keeps what it has.
- **Transport** goes through `glass-gateway-providers`, still the only
  crate that leaves the machine: HTTPS, except plain HTTP to a loopback
  address when `[managed] allow_insecure_http` is set (development and
  tests only; the signature, not the channel, is what devices trust).
- The device **reports** counts and names only (running agents, open
  asks, blocks in 24 hours, versions in force), never task text or paths.

### Catalog first (GA-2)
`catalog.search` (`crates/apps/catalog`) is a read-only action at Auto:
given a need in a sentence, it returns approved items the user may
install, best match first, each with its declared privileges. It searches
the device's synced catalog only, and scopes results by the user's
groups as the runtime resolved them when the task started
(`TaskContext::groups`, from policy), never by anything in the request:
an item none of the user's groups gets, or one any of them blocks, is
never returned. It is audited like every action.

## Consequences
- Two workspaces depend on `glass-managed`; changing it is changing a
  wire contract between our cloud and every device. Add fields with
  `#[serde(default)]`.
- Group membership travels inside each policy release until SCIM-backed
  device identity exists: every device gets the whole org's membership.
  Fine for pilots; at fleet scale membership should come per device.
- The catalog says who may *install* an item; policy still says who may
  *run* an agent (`[[group]] agents`). Approving an agent for a group
  doesn't yet allow it in policy; the console shows both.
- Declared privileges are shown and searched, but the runtime doesn't
  yet intersect them with policy (ADR 0008's `effective = declaration ∩
  policy ∩ scope`).
- An offline device enforces its last policy indefinitely; whether it
  should expire (ADR 0021) is still open.
